PI Agent Context Guide

How to fill the Markdown files

The goal is not to write lots of documentation. The goal is to give the agent the smallest useful amount of context that reliably produces the right change.

1. Be specific

Write rules the agent can act on. Prefer “Run npm test after changing API code” over “Keep quality high.”

2. Keep layers separate

Rules and conventions belong in reference files. Current task state belongs in working artifacts.

3. Scope aggressively

Each stage should name exactly what it needs. Don't make the agent discover the whole repository every time.

4. Improve the source

If you repeatedly fix the same output manually, turn that correction into a rule, example, test, or stage instruction.

The mental model

CLAUDE.md = Where am I?
CONTEXT.md = Where do I go?
Stage CONTEXT.md = What do I do?
references/*.md = What rules apply?
output/ = What am I working with?

This follows the methodology's five-layer hierarchy: structural routing in Layers 0–2, then stable reference material and changing working artifacts in Layers 3–4. fileciteturn1file6L329-L350

2. Root CONTEXT.md

Think of this as the map. It should answer: “Given what the user wants, where should I work?”

  • List the major workflows.
  • Point each workflow to its stage.
  • Point to shared references only when useful.
  • Keep it routing-oriented.

3. Stage CONTEXT.md

This is the most important file. Treat it as a contract, not a prompt essay.

The methodology explicitly recommends an Inputs → Process → Outputs contract, with the Inputs section specifying the exact reference and working files the stage should load. fileciteturn1file4L260-L266

# Stage: 01 Plan

## Goal
Turn the user's request into a small, implementation-ready plan.

## Inputs
- User request
- `../../_config/architecture.md`
- `../../_config/conventions.md`
- Relevant repository files discovered during inspection

## Process
1. Inspect the existing implementation before proposing changes.
2. Identify the smallest viable change.
3. Check existing patterns before introducing a new abstraction.
4. List files that need changing.
5. Define acceptance criteria.

## Outputs
Write:
- `output/plan.md`

The plan must contain:
- Problem
- Proposed change
- Files affected
- Acceptance criteria
- Risks / unknowns

## Verify
- Every proposed change maps to the user request.
- No unnecessary architecture changes.
- Acceptance criteria are testable.

## Stop
Do not implement code in this stage.

4. Reference Markdown files

Reference files are the project's factory configuration: stable rules the agent should internalize and apply across runs. The paper distinguishes them from working artifacts, which are the changing inputs/outputs of a particular run. fileciteturn1file0L11-L21

architecture.md

Only durable architectural decisions, boundaries, and important dependencies.

conventions.md

Actual code patterns: naming, file placement, error handling, API patterns.

testing.md

Commands, test locations, what must be tested, and known traps.

security.md

Only project-specific security constraints that agents must obey.

Write rules as decisions, not philosophy

Good:
- Use the repository's existing `Result` error pattern.
- API handlers live under `src/api/`.
- Prefer integration tests for database behavior.
- Do not expose internal database IDs in public API responses.

Weak:
- Write clean code.
- Follow best practices.
- Make the architecture scalable.
- Security is important.

5. Working artifacts

Put current-run information here: plans, investigation notes, task specifications, test results, implementation notes, and stage outputs. These change between runs, unlike reference material. fileciteturn1file0L26-L40

Rule: If deleting the file would make sense before starting a completely new task, it is probably a working artifact.

6. Don't make the agent read everything

The methodology's core idea is scoped context: each stage loads only what it needs. Its stage Inputs table is specifically intended to make that selection explicit and auditable. fileciteturn1file7L392-L405

  • Don't put all project documentation into one giant CONTEXT.md.
  • Don't link every reference from every stage.
  • Prefer one focused reference file over a giant “knowledge.md”.
  • If a stage doesn't need a document, don't load it.

7. Use examples where rules are hard to express

For coding agents, an example often communicates a convention faster than prose.

## API response pattern

Use this shape for successful responses:

{
  "data": ...,
  "meta": {...}
}

Use the existing error envelope for failures.
See: `src/api/errors.ts`.

8. Make “don't” rules rare but strong

Use prohibitions for things that are genuinely costly or dangerous.

## Do not
- Do not rewrite working modules to match a preferred style.
- Do not add a dependency when the existing stack can solve the problem.
- Do not change database schema without a migration.
- Do not remove tests just because they are inconvenient.

Avoid dozens of “never” rules. Too many constraints make the file noisy and harder to maintain.

9. Put verification inside the stage

Don't rely on a final vague instruction like “make sure it works.” Define what success means at the stage boundary. The methodology suggests extending stage contracts with verification criteria that check consistency against earlier outputs. fileciteturn1file5L280-L290

## Verify
- Typecheck passes.
- Relevant tests pass.
- No unrelated files changed.
- Acceptance criteria in `output/plan.md` are satisfied.

10. Human edits are feedback

If you repeatedly correct the same generated behavior, don't just keep editing the output. Ask whether the source context is underspecified. The paper's “edit-source” principle recommends turning recurring output corrections into better stage instructions or reference material. fileciteturn1file5L294-L314

Repeated correctionLikely fix
Agent keeps overengineeringAdd a concrete simplicity rule to conventions/stage contract.
Agent keeps putting files in wrong placesImprove repository map and file-placement rules.
Agent forgets testsAdd explicit verification + test command to the stage.
Agent changes unrelated codeAdd scope boundary: “Only modify files required for X.”
Agent repeats a known bug patternAdd the pattern + example to the relevant reference file.

11. PI-specific recommendation: start smaller than the paper

You do not need a five-stage workflow for every coding project. The paper's approach is strongest for sequential, reviewable, repeatable workflows; it explicitly says it is not a replacement for systems needing real-time multi-agent collaboration, high concurrency, or complex automated branching. fileciteturn1file2L137-L146

For a normal PI coding project, start with:

project/
├── CLAUDE.md
├── CONTEXT.md
├── _config/
│   ├── architecture.md
│   ├── conventions.md
│   └── testing.md
├── stages/
│   ├── 01_plan/
│   │   ├── CONTEXT.md
│   │   └── output/
│   ├── 02_implement/
│   │   ├── CONTEXT.md
│   │   └── output/
│   └── 03_verify/
│       ├── CONTEXT.md
│       └── output/
└── src/

12. The “good enough” test

Before adding anything to an MD file, ask:

1. Does the agent need this to make a better decision?
2. Is it stable enough to belong in this layer?
3. Can I state it in one or two precise sentences?
4. Does a concrete example make it clearer?
5. Will this still be true in a month?

Quick maintenance loop

Agent makes mistake
      ↓
Was it a one-off?
      ├─ Yes → fix output and continue
      └─ No
          ↓
What caused it?
          ├─ Missing project rule → update _config/*.md
          ├─ Wrong workflow instruction → update stage CONTEXT.md
          ├─ Wrong routing → update root CONTEXT.md
          └─ Missing capability → change code/tooling
          ↓
Run again
          ↓
Keep the MD change if it prevents recurrence

Bottom line

Don't try to make the MD files comprehensive. Make them decisive.

The folder hierarchy should tell the agent where to look; each stage should tell it what to do; reference files should tell it what rules to follow; and outputs should give the next stage a clean, inspectable handoff. That is the useful part of the methodology for PI projects. fileciteturn1file0L22-L40
